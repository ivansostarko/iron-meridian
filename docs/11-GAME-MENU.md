# Game Menu — Background Imagery

The register of every background image in Iron Meridian — its file, the screens it appears on, and what it is for.

> **Keep this file current.** Every background image added to the game must be recorded in §2 with its path, the screens it is used on, and a description, in the same commit that introduces it. See [Rules](#rules) at the bottom.

---

## 1. Architecture

```
Assets/Scripts/UI/
  BackgroundCatalog.cs   the register in code: id → resource path, scrim, description
  UIFactory.cs           CreateScreenBackground(...) builds the layered background
```

Screens never load a background texture themselves. One call, placed first so it sits at the back:

```csharp
UIFactory.CreateScreenBackground(canvas.transform, BackgroundId.Default);

// …or with a heavier scrim where legibility matters more than atmosphere:
UIFactory.CreateScreenBackground(canvas.transform, BackgroundId.Default,
    BackgroundCatalog.DenseScreenScrim);
```

### Layer stack

`CreateScreenBackground` builds three layers, back to front:

| Layer | Purpose |
|---|---|
| **Base** — opaque panel in `GameConfig.UiBackground` | Shows through if the image fails to load and covers any gap while `Resources.Load` runs. A screen can never end up transparent. |
| **Artwork** — `Image` + `AspectRatioFitter` (`EnvelopeParent`) | Covers the screen at any window aspect **without distorting the art**. Overflow falls outside the canvas rather than being masked — a `Mask` would cost an extra draw call for no visible difference. |
| **Scrim** — semi-transparent panel in the UI background colour | Knocks the artwork back so text stays readable. Opacity is the dial for how much of the art survives. |

All three layers set `raycastTarget = false`, so the background never intercepts clicks meant for the UI above it.

### Design rules the builder enforces

| Rule | Reason |
|---|---|
| **Images live under `Assets/Resources/`.** | The project builds every scene from code, so there is no serialised field to hold a `Sprite`. `Resources.Load` is the only runtime lookup path — the same constraint that governs icons, audio, VFX prefabs and 3D models. |
| **Never stretch artwork to fit.** | `EnvelopeParent` preserves the aspect ratio. A plain stretched `Image` distorts the art on any window that is not the authored aspect. |
| **Every background carries a scrim.** | Artwork behind live UI must lose contrast or the text stops being readable. |
| **Scrim levels live in `BackgroundCatalog`,** not at the call site. | One place to tune the look. |

### Fallbacks

A `BackgroundDef` may name a `fallback`. The three rows above have no image file
yet and fall back to the default artwork, so those screens look finished rather
than showing a flat colour — which reads as broken rather than as unbuilt.

**Adding the real artwork is the whole of the work.** Drop a PNG at the resource
path the row names and it is used on the next run; no code change, no catalogue
change. `UIFactory.CreateScreenBackground` walks the chain (bounded to four hops,
so a catalogue edit that makes a loop cannot hang the screen it was meant to
decorate).

Id in code: `BackgroundId.Default`.

### 3.1 The main menu board

`MainMenuUI` lays the menu out as a command board down the left-hand edge: the
logo, a scrolling list of entries, then the version line.

**The field fades, it does not end.** The board stands on a solid dark column as
wide as the interface, followed by ~260 px of gradient into the artwork
(`UIFactory.CreateHorizontalFade`). A flat panel with a hairline down its edge
reads as a dialog laid over a photograph; a gradient reads as shadow, and the map
appears to run *under* the interface. The solid part stops past the rows on
purpose — a gradient that started at the screen edge would be palest exactly
where each entry's second line is, and contrast under the text is the field's
whole job.

**The rows are flat, not cards.** Six hairline-bordered panels with gaps between
them is six frames the eye has to cross to read a list of six things. The entries
are now one column of faint fills divided by rules, with a glyph column behind a
rule of its own; the border is what the *hover* adds, along with an accent strip
down the leading edge, a lift in the fill and a white title. One vertical
hairline — the spine — runs down the board's leading edge behind the logo and the
list, and the version line's accent tick closes it at the bottom.

**What is deliberately not there.** The `OPERATIONS` / `REFERENCE` / `SYSTEM`
group headings and the descriptive blurb under the masthead were removed. Each
entry already states what it is on its own second line, so the headings were
captions over captions; between them the two devices cost roughly 150 px of the
vertical space the entries needed. Ordering carries the argument the groups used
to make — play first, reference next, system last — and `QUIT` stays at the
bottom of the list, furthest from where the cursor comes to rest. Position, not a
heading, is what keeps it out of the way.

**The list scrolls.** The entries are children of a `VerticalLayoutGroup` in a
scroll view spanning the board from `MenuTop` to `MenuBottom`. Fixed offsets were
fine for six entries at 1080p and would have run off the bottom at 1280×720 or
with a seventh entry added.

**The scrollbar shows itself only when it is needed** — `autoHideScrollbar` on
`UIFactory.CreateScrollView`, which sets Unity's own `ScrollbarVisibility.AutoHide`.
A bar that is always there says "there is more below" when there is not, and on a
list whose length depends on the window that is a permanent small lie. The
viewport keeps its inset either way, so nothing reflows as the bar comes and goes.

**There is no "Esc — quit" caption.** `QUIT` is the last row of the list, in
words, where somebody looking for the way out will look; a shortcut caption under
it was a second answer to a question the menu had already answered. Escape still
opens the quit dialog — see `MainMenuUI.Update`.

### 3.1a The opening film

`IntroVideoUI` plays `Assets/Resources/Videos/intro-video/game_intro.mp4` once per
launch, over a black screen, on its own canvas at sorting order **1000** — above
everything the game builds, the loading overlay's 500 included. The main menu is
built behind it either way; the only thing that waits is the menu music, which
would otherwise play under a film that has a score of its own.

| Rule | How |
|---|---|
| **It always ends** | Three independent dismissals — the clip reaching its end, any input, and a 120 s timeout — and the continuation runs exactly once whichever gets there first. Same rule the loaders are held to (`docs/12-LOADERS.md`), for the same reason: a film that could trap the player is worse than no film. |
| **Any input skips it** | `Input.anyKeyDown`, which covers the keyboard and the mouse. Not a labelled button: an opening film is a thing people sit through once and skip forever after. A faint "Press any key to skip" in the corner says so rather than making them guess. |
| **Once per process** | A static flag, not a `PlayerPrefs` entry — backing out of a screen to the main menu does not replay it, but every launch runs it. |
| **A missing file is not an error** | It warns once and the menu comes up. |
| **Escape belongs to the film** | `MainMenuUI.Update` returns early while `IntroVideoUI.Showing`, so Escape skips the video instead of opening the quit dialog behind it. |

The picture is decoded to a `RenderTexture` and shown on a `RawImage` fitted with
`FitInParent` — **fit, not envelope**. A background image may be cropped; a film
frame is composed, so it is letterboxed against the black instead. Its audio goes
through an `AudioSource` rather than the video player's Direct mode, so it obeys
the master volume like everything else.

### 3.2 The BACK control

Every menu screen's BACK button comes from `UIFactory.CreateBackButton`.

It used to be a plain `CreateButton` with a "&lt; BACK" caption — a flat slab
whose only affordance was the word on it, sitting on full-bleed artwork where a
mid-grey rectangle has nothing to separate it from the photograph behind. The
shared control borrows all three of its devices from the main menu's own entries,
so the screens read as one interface: a hairline-bordered surface so the control
has an edge of its own, an accent strip down its leading edge that widens under
the cursor, and a `UiIcons.ArrowLeft` glyph so the direction is legible before the
label is read.

Used by `PlaceholderScreenUI` (Single Player, Multiplayer, Extras), `TestingUI`,
`SettingsUI`, `EastFranceUI` and `UnitsListUI`. Each passes its own anchor and
position; the default is the top-left corner.

### 3.3 The settings screen

`SettingsUI` is a **vertical tab rail** down the left with one scrolling page
beside it. The tabs used to be two 600 px slabs across the top, which spent a
whole band of the screen saying "VIDEO" and "AUDIO" and left nowhere for a third
to go — a horizontal bar fits the number of tabs it was drawn for. The rail grows
downward for nothing and uses the same accent-strip device as the main menu's
rows and the editor's nav.

**Every control does something.** A settings page whose switches write a
preference and change nothing teaches the player that the screen is broken.

| Page | Rows |
|---|---|
| **VIDEO** | Resolution · window mode · **APPLY** · quality preset · anti-aliasing · shadows · texture quality · anisotropic filtering · V-Sync · frame-rate cap |
| **AUDIO** | Master volume · music · weather ambience · effects · interface · hover sounds on/off |
| **CONTROLS** | Every key and mouse button, grouped by camera · selection · orders · map editor · screens |

**CONTROLS is a reference, not a rebinder.** The game reads `UnityEngine.Input`
against fixed `KeyCode`s (golden rule 5), so there is nothing to rebind yet — and
a page of dropdowns writing a preference nothing reads would be worse than a page
that is honest about what it is. What a player needs today is to find out that
**C** sets a formation's facing, which nothing on the map screen says.

It is grouped by *what you are doing*, not by device: a list sorted by key can
only be used by someone who already knows the key. Keys are drawn as chips laid
out from the right, so every row's keys end on the same edge whatever their
number and length; chip widths come from the label, because "Middle-drag" and "W"
are both keys and a column of equal caps would either clip one or float the
other. The word "or" between alternatives is drawn as text — it is the one thing
in the row that is not something you press.

Resolution and window mode wait for **APPLY** — they cost a display-mode switch.
Everything else takes effect as it is moved, because the point of a shadow or a
volume control is seeing and hearing what you are choosing.

Video settings live in `Core/DisplaySettings.cs` (`PlayerPrefs` under `im.gfx.*`)
and are applied by `DisplaySettings.Apply()`, called from the main menu on every
visit — a setting the player chose has to survive a restart, and the screen that
*changes* it cannot be the only thing that knows it. The quality **preset** is
pushed first and on its own: switching level rewrites shadows, anti-aliasing and
the rest wholesale, so anything set before it would be thrown away by it.

Audio levels live in `AudioManager` (`im.vol.*`) — see `docs/10-AUDIO.md`.

## 4. Import settings

The background currently uses Unity's import defaults. Recommended for full-screen artwork:

| Setting | Value | Reason |
|---|---|---|
| Texture Type | Sprite (2D and UI) | Required for `Sprite.Create` / `Image`. |
| Generate Mip Maps | Off | The image is drawn at roughly 1:1 on screen; mips cost 33 % more memory and soften it. |
| Max Size | 2048 | Ample for a 1920-wide reference canvas. |
| Compression | High quality, or Crunched for build size | An uncompressed 4K RGBA background is ~64 MB in VRAM. |
| Filter Mode | Bilinear | Smooth when enveloped past 1:1. |

The source file is a 2.9 MB PNG; compression settings affect runtime memory, not the file on disk.

## 5. Adding a new background

1. **Place the image under `Assets/Resources/Graphics/Backgrounds/`.** Anywhere else and it cannot be loaded at runtime.
2. **Set import settings** per §4.
3. **Add a `BackgroundId` value and a `BackgroundDef` row** in `BackgroundCatalog`, including its scrim level and description.
4. **Call `UIFactory.CreateScreenBackground(canvas.transform, BackgroundId.<New>)`** as the first thing added to the canvas, so it sits behind the UI.
5. **Check legibility** at 16:9 and at an unusual aspect (very wide or a tall window). Raise the scrim rather than dimming the artwork in an image editor.
6. **Update this file** — the register in §2 *and* the coverage table in §3, with path, screens and description.
7. **Record the source** and licence/URL for any purchased or downloaded artwork.

## Rules

1. **This document is the register of every background image in the game.** Adding, replacing or removing one, or using one on a new screen, is not done until §2 and §3 here are updated in the same commit — with the file path, the screens it is used on, and a description.
2. Background images live under `Assets/Resources/`; nothing else is loadable at runtime.
3. Screens call `UIFactory.CreateScreenBackground`. No `Resources.Load` of a background at a call site, and no hand-rolled full-screen `Image`.
4. Artwork is never stretched — aspect ratio is preserved by envelope-fitting.
5. Scrim levels live in `BackgroundCatalog`, not at call sites.
6. Backgrounds must degrade gracefully: a missing image warns once and leaves the opaque base colour, never a transparent or white screen.
7. Record the source and licence of every imported image.
