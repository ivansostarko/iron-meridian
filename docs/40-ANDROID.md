# Android

Iron Meridian on a phone or tablet: what had to change, what the build needs, and
what is still missing.

**Status: the port is prepared, not shipped.** Everything below is in the
repository and compiles, and nothing here has been run on a device — see §8
before you promise it to anybody.

---

## 1. The two things that actually made it possible

Most of a Unity game is portable. Two things in this one were not, and both would
have failed silently rather than loudly.

### 1a. StreamingAssets is not a folder on Android

On Windows, macOS and Linux, `Application.streamingAssetsPath` is a directory
beside the player and `File.ReadAllText` works. On **Android it is a
`jar:file://…!/assets/…` URL into the APK**. `System.IO` knows nothing about it:
every `File.Exists` returns false and every read throws.

Five things in this game live there — the unit catalogue, the formation names,
the mission list, the shipped scenarios and the Cesium ion token — so the failure
mode was an empty globe with no units on it and nothing in the log saying why.

Every one of those reads now goes through **`Core/StreamingAssetsFile.cs`**:

| Platform | How it reads |
|---|---|
| Desktop | `File.ReadAllText` — unchanged |
| Android | `UnityWebRequest`, which is the only API that can open a jar entry |

**The Android read is synchronous on purpose.** `UnityWebRequest` is
asynchronous; the loaders that need these files are not, and are called lazily
from wherever a unit definition is first asked for. Making them async would mean
an `await` at every call site and an ordering guarantee across sixteen scenes, to
save a wait on a *local decompression* of a few milliseconds. The spin is bounded
by a ten-second timeout so a pathological case reports rather than hangs, and it
is safe for a `jar:`/`file:` URL specifically — Unity services those on a worker
thread and does not need the main loop to come back round. It would **not** be
safe for an `http` one, and nothing here reads over the network.

**Writes never go through it.** StreamingAssets is read-only in a build on every
platform. Everything the player changes — saves, tuning, the mission book — is
already in `Application.persistentDataPath`, which is a real directory on Android
too.

### 1b. Android cannot list a directory inside the APK

`SaveSystem.ListMaps` walked `StreamingAssets/Maps`. There is no folder to walk.

The build now writes **`StreamingAssets/Maps/index.json`** naming what it packed,
and `ShippedMaps()` reads that. It is generated by
`ProjectBootstrap.SetupProject`, which every build script runs first, so the
index cannot drift from the folder it describes. On desktop the folder is *also*
walked, so a scenario dropped in by hand while the editor is open still appears
without regenerating anything.

Add a scenario and you get the index for free. Add one and skip setup, and it
ships in the APK and cannot be opened.

## 2. Touch

The game is built on legacy `UnityEngine.Input` and a mouse. Unity already maps a
single touch onto mouse button 0 and `Input.mousePosition`, so **tapping to
select, to place and to press a button works with nothing done to it**.

What has no touch equivalent at all is the right button, the wheel and the middle
button — and those carry ordering a move, zooming and orbiting, which is most of
the game. `Core/TouchInput.cs` defines those gestures once, and the handful of
places that need them read it, instead of thirty-odd `Input.GetMouseButton` call
sites each learning about touch.

| Mouse | Touch | Read by |
|---|---|---|
| Left click | Tap | Unity, for free |
| **Right click** | **Long press** (0.45 s, then lift) | `SelectionManager` |
| **Wheel** | **Pinch** | `CameraRig` |
| **Middle drag** | **Two-finger twist** = orbit, **two-finger drag up/down** = tilt | `CameraRig` |
| WASD | **One-finger drag on the map** | `CameraRig` |
| Box select (drag) | — **not available**, see below | `SelectionManager` |
| `Esc` | **Back button** | Unity maps it to `KeyCode.Escape`, for free |

**A long press commits on release, not on the timer.** Firing when the clock runs
out means the map acts under a finger that has not decided yet. Moving more than
24 px cancels it, because a press that turned into a drag was a pan.

**A drag pans and never box-selects.** One finger cannot do both, and panning
is the one that has no alternative — there is no WASD on a phone, whereas a box
selection can be replaced by tapping counters one at a time. So `SelectionManager`
does not start a selection box on a touch platform.

**A drag moves the ground under the finger** — the opposite sign to a key. `D`
means "look right"; dragging left means "pull the map left". Getting that
backwards is the most obvious way a touch port feels wrong.

That the back button is `Escape` matters more than it sounds: every armed tool in
the editor — the effect placer, the obstacle tool, the strike callers, the
placement ring — already cancels on `Escape`, so all of them got a working cancel
gesture without being touched.

### 2a. The interface is scaled up, not re-laid-out

`UIFactory.ReferenceResolution` is **1280×720 on a handheld** and 1920×1080
everywhere else. The layout is authored in those units, so a smaller reference
makes every control physically bigger: the rail's rows and the map cluster's
buttons land at roughly a finger's width on a 6-inch screen, where at the
desktop's reference they are about 6 mm and are missed as often as hit.

It is a scale change, not a layout change. Nothing moves relative to anything
else, and less of the map is visible around the chrome — which is the trade a
small screen makes anyway.

## 3. What is switched off on Android

| Feature | Why |
|---|---|
| **Video recording** (`docs/39-CAPTURE.md`) | It shells out to ffmpeg. An Android app cannot spawn an arbitrary executable, there is no PATH to find one on, and `System.Diagnostics.Process` is not in the APK's runtime. `CaptureSystem.CanRecord` is false, so the button says so rather than failing when pressed |
| **Screenshots** | Still work. They go to `persistentDataPath` instead of Pictures, because writing to the gallery needs a storage permission this app does not ask for |
| **Steam** (`docs/36-STEAM.md`) | Already behind the `IRONMERIDIAN_STEAM` define and never set for Android |

## 4. Building

### 4a. What the machine needs

Unity Hub → Installs → the 6000.0 editor → **Add modules**:

- Android Build Support
- OpenJDK
- Android SDK & NDK Tools

`make doctor` reports whether all of that is there, and whether `adb` is on PATH.

### 4b. The jobs

| Command | What it does |
|---|---|
| `make android` | An installable **APK** into `Builds\Android` |
| `make android-aab` | An **App Bundle** (`.aab`) for Google Play |
| `make android-install` | A development APK, `adb install -r`'d onto the attached device |

All three run `scripts/build-android.ps1`, which runs `SetupProject` first — the
same as the Windows build, and the reason the map index is always current.

### 4c. Signing

**Never defaulted, never written down.** Give all four or none:

```powershell
.\scripts\build-android.ps1 -Aab `
    -Keystore .\keys\release.keystore -KeystorePass $env:IM_KS_PASS `
    -KeyAlias ironmeridian -KeyPass $env:IM_KEY_PASS
```

Unsigned, Unity signs with its debug key: that installs on a device and is
rejected by Play, which is the right way round for a build you ran by accident.

Keep the keystore **out of the repository** — the same rule as the ion token
(golden rule 1). Losing it means never updating the app on Play again.

## 5. Player settings

Applied by `AndroidBuild.ApplySettings`, in code rather than in the `.asset`
files, so a fresh clone builds the same app.

| Setting | Value | Why |
|---|---|---|
| Package name | `me.ivansostarko.ironmeridian` | Changing it after release makes a *different app*, saves and all — so it is a constant |
| Scripting backend | IL2CPP | Mono is not an option for a 64-bit Android build |
| Architecture | ARM64 only | Play has required 64-bit since 2019; x86_64 is emulator-only and doubles the APK |
| Min SDK | 26 (Oreo) | Cesium's native is built against a modern NDK, and devices below it cannot stream 3D terrain anyway |
| Graphics | Vulkan, then GLES3 | Terrain shading is driver-sensitive; the fallback means a bad Vulkan driver still starts |
| Orientation | Landscape only | A map is read across, and every panel is laid out against a landscape canvas |
| Internet permission | Forced | The terrain streams from Cesium ion; the app is useless without it |

## 6. The ion token on a device

Same two options as everywhere else (`docs/02-CESIUM.md`): the file, or the
constant. **The file now works on Android** because it goes through
`StreamingAssetsFile` like everything else.

The warning is the same and it is worth repeating here, because an APK is easier
to hand around than an installer: `Assets/StreamingAssets/cesium-token.txt` is
packed into the APK in plain text and **anyone can read it out of one**. The
Windows installer strips it unless `-IncludeToken` is passed (`docs/34-INSTALLER.md`
§2a); the Android build has **no equivalent strip yet** — see §8.

---

## 7. Cesium on Android

Cesium for Unity 1.25 ships `libCesiumForUnityNative.so` for `arm64` and
`x86_64`, so terrain streaming needs nothing added. What it does need is
bandwidth and memory: tiles are fetched over the network and held in RAM, and the
tile budget that suits a desktop is not the one that suits a phone. Tuning that
is §8 work, not something this port has measured.

## 8. Known gaps

Honest list. None of this is done.

- **Nothing has been run on a device.** The port compiles and the pieces are
  wired; the first APK will find things this list does not.
- **No token strip for Android.** The Windows installer leaves the ion token out
  unless asked; `build-android.ps1` has no such switch, so an APK built from a
  working tree carries the token. Do not hand one out.
- **The map editor is a desktop interface.** Seventeen rail sections, a
  right-hand inspector and a strike dock on a 6-inch screen is not a design
  anybody chose; it fits, and that is all that can be said for it. A phone
  probably wants the mission player and not the editor.
- **No tile budget for mobile.** Cesium's memory and screen-space-error settings
  are the desktop's.
- **`make check` does not compile for Android.** Roslyn against Unity's reference
  assemblies catches C# errors, not IL2CPP or native-plugin ones.
- **The long press has no visual feedback.** `TouchInput.LongPressPending` is
  there for a ring or a cursor change and nothing draws it yet, so the gesture is
  invisible until it fires.
- **No box selection.** A drag pans, so there is no gesture for selecting
  several formations at once. Two-finger tap, or a lasso mode on a toolbar
  button, are the obvious candidates.
- **No haptics, no back-button confirmation.** Back is `Escape` everywhere, which
  in the main menu means it does nothing rather than asking to quit.
